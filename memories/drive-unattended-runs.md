**In an explicitly unattended run — "keep going," an autonomous goal, an overnight session — the whole value is endurance, and what kills it is *stopping*: ending the turn and handing control back.** Narrating as you go is the opposite of the problem — it's wanted. The failure modes are all forms of stopping: winding down to report, re-litigating a step you're already cleared to take, or handing the turn back just to wait. Sustain forward motion until there's genuinely no unblocked work left. (This is about *autonomous* contexts; in normal interactive chat the usual check-in and clarify instincts still apply — see [[ask-questions-in-plain-text]], [[close-loops-in-session]].)

**Sustain one long multi-step push; narrate freely, just don't *stop*.** Do the work across many tool calls per turn, and announce progress as you go — narration and per-increment commit messages are wanted, not the problem. What's not wanted is *ending the turn*: don't wind down with a status summary and an implicit "which next?" while there's unblocked work, and don't treat a milestone landing as a place to stop. "Context is heavy" is not a reason to wind down either — if quality is genuinely at risk, say so once and continue at the best increment.

**Bias to action on the authorized path — the run's authorizations ARE the permission.** Re-litigating an authorized, reversible step (open a PR, deploy to a preview / "anything-goes" environment, make a lint or config change) wastes the binding constraint — context — and reads as timidity. Make the reversible call and keep going; watch the result asynchronously and pivot or surface only if it actually goes wrong. Decide among threads in a sentence, then execute — don't write paragraphs comparing options. Re-deriving what you already know is the tax.

**Wait actively; never yield just to wait.** When you're blocked on something external the harness won't notify you about — CI, a background job, a remote queue — don't hand the turn back to merely wait on it. Wait with a mechanism that wakes you when the work is done: a backgrounded loop that exits on the condition, a stream monitor, or a scheduled wake-up. **Combine the trigger with a fallback timeout set longer than the expected return time**, so a signal that never arrives can't hang the run forever. And while the bottleneck bakes, keep the *parallel* frontier — the rest of the open, unblocked work — moving rather than just watching it bake; see [[dont-fake-blocked-in-unattended-runs]]. Yielding-and-summarizing while you wait burns the user's attention for nothing.

**Plan the run as several independent tracks, not one.** A long session pointed at a single linear track can be derailed by the first blocker, wasting the whole window. Going in — and as you learn more — keep a loose, reorderable map of where the work can branch: several avenues that don't depend on each other, so that when one blocks you always have somewhere to pivot. The plan is a map, not a contract; let real progress reorder it, and don't follow it past its expiry.

**Pivot on blockers; the stop condition is "every remaining avenue is blocked-on-a-human or done" — not "a blocker exists."** When something blocks, record it where the user will actually see it and pivot to the next ready track — repeat. Before you *believe* an avenue is blocked, prove the frontier is actually exhausted rather than assuming it: decompose the open work and check what genuinely needs-a-human vs. what you simply haven't attempted yet — [[dont-fake-blocked-in-unattended-runs]] is that test. (Stopping and active-wait aren't in tension: stop *spawning new* work once only bottleneck-bound items remain, but keep the active-wait mechanism running so the signal still wakes you.) Surface only genuine decision-forks (architecture, scope, product/UX calls that are truly the user's), and surface them *asynchronously* (a question board, a review doc) while continuing other unblocked work. Never halt the whole run on one fork. Sub-decisions on naming, ordering, and commit boundaries are yours to make. Keep the shared state in durable artifacts the user actually reads (PRs, issues, docs) — a private/internal task list is your scratchpad, not the deliverable.

**Drive to the literal end-state, not a pile of verified pieces.** "Done" lives at the last mile — the change running in the real target environment — not at a stack of locally-verified parts.
